# M0 Findings

**Date:** 2026-08-17
**Toolchain:** Flutter 3.38.3 · Dart 3.10.1 · Xcode 26.6 · Android SDK 35 · JDK 17
**Devices:** iPhone 17 simulator (iOS 26.5) · Android emulator `m0_test` (API 35, arm64)

## Headline

The migration path works **on both platforms**. A real v7 save, planted exactly the
way the Capacitor build writes it, is readable from Dart and round-trips without
losing a field. That was the finding M0 existed to produce, and it lands in favour
of the design.

## Save bridge

| Check | iOS | Android |
|---|---|---|
| Reads save planted in the Capacitor native store | **pass** | **pass** |
| Returns null when absent | **pass** | **pass** |
| 200KB payload survives | **pass** | **pass** |
| Real v7 fixture round-trips lossless end to end | **pass** | **pass** |
| Native handler compiles | **pass** | **pass** |

**Key formats confirmed from the plugin source** (`@capacitor/preferences`), not
guessed:

- **Android** — `Preferences.java` calls
  `context.getSharedPreferences("CapacitorStorage", MODE_PRIVATE)` and stores keys
  **unprefixed**, so the key is `mergeEmpireFC_save_native`.
- **iOS** — `Preferences.swift` computes `prefix = group + "."` and applies it on
  every access, so the key is `CapacitorStorage.mergeEmpireFC_save_native`.

These differ, and the difference is load-bearing. Unifying them would read `nil` on
a device that actually holds the save. Both are now verified behaviour.

Android matters more than iOS here: the native mirror exists specifically to
survive Android One UI storage eviction, which is the failure mode that motivated
`nativeSaveMirror.js` in the first place.

### Reproducing the Android run

The machine had no AVD and no system image. To recreate:

```bash
export ANDROID_SDK_ROOT=/opt/homebrew/share/android-commandlinetools
sdkmanager --install "system-images;android-35;google_apis;arm64-v8a"   # ~3.8GB
avdmanager create avd -n m0_test -k "system-images;android-35;google_apis;arm64-v8a"
$ANDROID_SDK_ROOT/emulator/emulator -avd m0_test -no-window -no-audio -no-snapshot &
flutter test integration_test/ -d emulator-5554
```

Note the pre-existing AVD `Medium_Phone_API_36.1` does *not* work — it targets an
`android-36.1` image that is not installed.

### Why no numbers

Frame timings from this session would be worthless, and reporting them would be
worse than reporting nothing:

1. `traceAction` only persists timings under `flutter drive`, not `flutter test`.
   A `test_driver/integration_test.dart` entry point is committed so the real run
   is a one-liner.
2. Profile mode is not supported on the iOS Simulator at all, and debug-mode
   timings are dominated by the debug renderer.
3. Simulator GPU behaviour does not predict device GPU behaviour.

**To get the real answer**, on a physical device:

```bash
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/diorama_perf_test.dart --profile -d <device>
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/card_perf_test.dart --profile -d <device>
```

The bar is a 60fps budget: average frame build under 16ms, no sustained jank.

## Spec deviations

1. **`flutter_lints` is ^6.0.0**, not the ^5.0.0 the plan assumed. Used the version
   the SDK ships with.
2. **CI runs on `ubuntu-latest`**, not `macos-latest`. Unit and widget tests need no
   Apple toolchain; M7 adds a macOS job for iOS release builds.
3. **Plan bug, fixed:** the diorama probe gave every rain drop the same
   `ValueKey('rain-drop')`. Keyed siblings must be unique, so it threw
   "Duplicate keys found". Keys are now indexed and the test matches on prefix.
4. **Two codec tests added** beyond the plan. A default save has an empty grid, so
   the planned null-preservation test proved little; there is now a test that plants
   cards at sparse indices (0, 7, 38) and asserts positions and the 36 intervening
   nulls survive. A second added test asserts ints are not coerced to doubles, which
   would change the bytes and break equality against the cloud copy.

## Carried into M3

**Rive for the manager-avatar walker.** The walker is an articulated figure with
separate near/far thigh, shin and arm animations (`psvThighN/F`, `psvShinN/F`,
`psvArmN/F`, plus `psvBob`), and the dugout cam adds idle rigs (`dcIdleBreath`,
`dcIdleWeight`, `dcIdleArmN/F`, `dcIdleHead`). Hand-rolling that limb maths in a
`CustomPainter` is the painful path. Evaluate Rive for the character rig, keeping
the painter/widget decision above for the scene *around* it — they are separable.

## Go/no-go for M1

**Go.** M1 ports data, state, utils and the 37 engines with their tests, and none of
that work depends on the one remaining open item. Profile-mode perf numbers on
physical hardware are the only outstanding M0 follow-up, and they gate M3, not M1.
